# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A time-distance (Marey) chart for CPTM railway Line 710 (São Paulo) train schedules. A Python CLI parses train schedule geometry out of an AutoCAD DXF drawing into JSON; a static vanilla-JS/SVG frontend renders the planned schedule as an interactive chart where dispatchers can drag station-time nodes and see the delay propagate downstream.

There is no build system, package manager, or server. Two independent pieces:

- `backend/` — Python 3 standard-library-only scripts (DXF parser + SQLite seeder)
- `frontend/` — a single static HTML/CSS/JS page, opened directly in a browser

## Commands

Run all commands from the `grafico/` project root (this directory).

```bash
# Parse the DXF drawing into backend/data/schedule.json
python3 backend/src/parser.py

# Run the parser unit tests
python3 -m unittest backend/tests/test_parser.py -v

# (Optional) Seed the SQLite DB from schedule.json — not wired to the frontend, see below
python3 backend/src/database.py
```

There is no npm/build step for the frontend. Open `frontend/src/index.html` directly in a browser, or serve `frontend/` with any static file server if you need `fetch()` of `../data/schedule.json` to work (opening via `file://` will fail CORS and silently fall back to the hardcoded `fallbackSchedule` in `app.js`).

Manual frontend test scenarios (no automated UI tests exist) are in `frontend/tests/manual_test.md`.

## Architecture

**The frontend is entirely client-side and does not talk to `database.py` or SQLite.** `database.py` is a standalone seeding script (reads `backend/data/schedule.json`, writes `backend/data/railway.db`) that exists per the original spec but nothing currently reads from it. The actual data flow implemented is:

```
L10 DOM.dxf --(backend/src/parser.py)--> backend/data/schedule.json --(fetch or manual upload)--> frontend (in-memory only)
```

- **DXF → JSON (`backend/src/parser.py`)**: Streams the DXF as text, watching for group codes `0` (entity type), `8` (layer), `10`/`20` (vertex X/Y). Only entities on layers `BFU-RGS` or `RGS-BFU` are kept as trips. X coordinates encode time (`coord_to_time`: 20 DXF units = 1 minute); Y coordinates encode station via nearest-match against a hardcoded `y_coordinate → station code` table (`get_station_code`, 50-unit snap tolerance). One row of stations (`stations_row1`) is Line 10, the other (`stations_row2`) is Line 7; they share the "Luz" station at different Y values, disambiguated downstream as `LUZ` vs `LUZ_L7`.
- **Frontend (`frontend/src/app.js`)**: A single file, no framework, no modules. `appState` is the sole source of truth in the browser tab (`trips` = working copy, `originalTrips` = pristine copy for reset/delta-from-original propagation). All chart geometry is generated by hand-building SVG DOM nodes (no charting library) — see `timeToX`/`xToTime` and `dxfYToSvg` for the coordinate mappings between clock time / DXF Y and SVG pixels. The `stations` object in `app.js` duplicates the station table from `parser.py`/`database.py` — if station Y-coordinates or line groupings change, all three places need updating together.
- **Node drag + propagation**: `onNodeDragStart`/`onNodeDrag`/`onNodeDragEnd` implement the core interaction. Dragging a node computes `deltaMinutes` versus that node's time in `originalTrips`, then shifts every downstream stop in the *current* trip by that same delta relative to *its own* original time (not relative to its pre-drag value) — this is why the delta is always computed against `originalTrips`, not `appState.trips`. "Export Grade" (`exportData`) downloads the in-memory `appState.trips` as JSON; it does not persist to any database. "Resetar" restores `appState.trips` from `originalTrips`.
- **Realized/actual data**: Currently only a hardcoded `mockRealizedData` array toggled via the "Mostrar Realizado" button — there is no live tracking ingestion (this matches spec.md FR-008, explicitly out of scope for this version).
